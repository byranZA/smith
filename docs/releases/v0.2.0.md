# smith v0.2.0

v0.1.1 hardened a box. v0.2.0 makes it a place to work: a blueprint declares the repos, packages, runtimes and files a box carries, smith installs itself on the box and converges that workspace, sessions give you one tmux session and one worktree per branch, and `smith loop` works a spec's GitHub tasks with a coding agent.

## What's new

- **Blueprints and preferences** in `~/.smith/`, validated offline by `smith blueprint check`, with `smith init` to write commented starters. → [Blueprints](../blueprints.md)
- **Making the box too:** a provider adapter describes your provider's CLI as data, and `smith machine create` creates a box and waits for SSH. → [Provider adapters](../providers.md)
- **Boxes by name:** setup registers the address it proved; `machine list`, `add` and `forget` manage the inventory. → [The box inventory](../inventory.md)
- **smith on the box:** setup installs smith on the box, verified against the release checksums, and relays verbs to it. `smith machine upgrade` moves it to your version. → [smith on the box](../on-box.md)
- **Config staging:** setup carries the blueprint, its placements and resolved env onto the box. → [Config staging](../on-box.md#config-staging)
- **The workspace stage:** placements, apt packages, mise-pinned runtimes and bare clones of every declared repo, with `smith workspace converge` to re-run it alone. It never deletes. → [The workspace stage](../workspace.md)
- **Sessions:** `session start`, `attach`, `list`, `stop` and `rm`, one tmux session and git worktree per branch, with a work-state readout of dirty trees and unpushed commits. → [Sessions](../sessions.md)
- **The loop:** `smith loop run <spec>` works a spec's GitHub sub-issues with `claude`, `codex` or `pi`, one task per run. Each task is worked in its own task worktree and lands on the spec's work branch, `smith/<n>-<slug>`, which is pushed after each closed task (`--no-push`, or `push: false` in the repo file, turns that off). → [The work branch](../loop.md#the-work-branch), [Pushing](../loop.md#pushing)
- **The loop's settings:** `--interactive` runs one task with the agent attached to your terminal, `.smith/repo.yaml` holds the repo's shared settings, and `smith repo init` writes it. → [The loop](../loop.md)
- **One task at a time:** `smith loop run <issue>` also takes a single task, standalone or a spec's child, and works only that task. → [What the loop reads from GitHub](../loop.md#what-the-loop-reads-from-github)
- **The loop on a box:** `smith loop run <box> <issue> --repo <name>` runs the loop in a loop-driven session on the box that outlives your connection. `session attach` watches it read-only by default, `--interact` jumps in, and `session list` shows how its run ended under `OUTCOME`. → [On a box](../loop.md#on-a-box---repo), [Loop-driven sessions](../sessions.md#loop-driven-sessions)
- **Stop reports:** however a run ends after its issue is admitted, the loop comments on the issue with its outcome and report. → [`smith loop run`](../loop.md#smith-loop-run)
- **Tasks marked as they are worked:** the loop labels a task `smith:working` while an agent runs on it, and hands a task it gives up on to you as `ready-for-human` and `smith:failed`, with a comment naming the machine, worktree and branch it left. → [`smith loop run`](../loop.md#smith-loop-run)
- **A broken agent stops the run:** when every attempt at a task is an agent failure, or the agent cannot start, the run stops as `agent broken` instead of handing every task to you. → [`smith loop run`](../loop.md#smith-loop-run)
- **Your triage labels:** `labels:` in the repo file renames the agent, human and spec labels the loop reads. → [Triage labels](../loop.md#triage-labels)
- **Worktree preparation:** before each agent attempt, and on `session start`, smith installs the toolchain the repo's mise config pins and runs the repo file's `prepare:` command. → [Worktree preparation](../sessions.md#worktree-preparation), [The prepare command](../loop.md#the-prepare-command)
- **The toolchain in every shell:** sessions run under `mise exec`, with the blueprint's `env`; a plain SSH login gets mise's shims through `/etc/profile.d/smith.sh`, without the `env` exported. → [What a shell on the box gets](../on-box.md#what-a-shell-on-the-box-gets)
- **A box that can clone and run the loop:** what a blueprint needs for a private repo and an agent's credentials, with a worked example. → [A box that can clone and run the loop](../blueprints.md#a-box-that-can-clone-and-run-the-loop)
- **Self-update:** `smith update` replaces your smith with the latest release, or the one `--version` names, checked against the release checksums, then offers to upgrade every box to it in one question. → [Update smith](../install.md#update-smith)
- **Renaming a box:** `smith machine rename` renames a registered box without re-running setup. → [Renaming a box](../inventory.md#renaming-a-box)
- **Setup applies the resolved configuration:** `access`, `terminal`, `workspace` and the git identity from a blueprint or your preferences now reach the box, and setup prints the access mode it resolved and where it came from. → [Every resolved field reaches the box](../blueprints.md#every-resolved-field-reaches-the-box)
- **Memory and swap:** setup warns when a box has less than 2 GB of memory, adds a swapfile where the disk allows, and sets an OOM policy so one killed process no longer takes its whole tmux session down. → [Memory and swap](../provisioning.md#memory-and-swap)
- **`blueprint check` names the references it cannot resolve** on your machine, so a missing env var or file shows up before setup. → [Checking before you build](../blueprints.md#checking-before-you-build)
- **Interrupting a run:** Ctrl-C removes what smith shipped to the box before exiting; a second Ctrl-C ends it at once. → [Provisioning](../provisioning.md#interrupting-a-run)

## Upgrading

- A box set up by an earlier candidate, `v0.2.0-rc.4` included, needs `smith machine upgrade <box>` and then `smith machine setup <box>`: setup's re-run installs the base packages and writes `/etc/profile.d/smith.sh` and the git identity in `~/.gitconfig`.
- A box set up by an earlier smith needs `machine setup` re-run from your machine, not only `machine upgrade`, before on-box verbs work. Setup now stages the resolved configuration onto the box as `/etc/smith/resolved.json`, and `session` and `workspace converge` refuse a box without it. → [Config staging](../on-box.md#config-staging)
- The same re-run adds the `swap` and `tmux-oom-policy` phases; until then `machine status` reports the box as partially provisioned, naming them. → [Boxes set up before the swap phase](../provisioning.md#boxes-set-up-before-the-swap-phase)
- A local `loop run` from an ordinary clone now puts its task worktrees in the state home, `~/.local/state/smith/worktrees/` (or under `$XDG_STATE_HOME`), not in the clone's `.git`, where Jest and other tools that skip `.git` paths found nothing to run. Remove anything an earlier candidate left under `.git/smith/worktrees/` with `git worktree remove <path>`; `git worktree list` shows them. → [The work branch](../loop.md#the-work-branch)
- Setup now takes `access` from a blueprint or your preferences when `--access` is not given. A public box whose config says `access: tailscale` moves to the tailnet on its next setup, which needs an auth key. A tailscale box re-run with nothing resolving `tailscale` is refused rather than reopened to public SSH: pass `--access tailscale` to keep it. → [Config staging](../on-box.md#config-staging)

## Fixes

- Every box gets `git`, `tmux`, `curl`, `ca-certificates` and `sudo` in setup's `packages` phase, so sessions work on a minimal image.
- The workspace's git identity is written to `~/.gitconfig`, where a placement at `~/.config/git/config` can no longer wipe it.
- The loop warns when the work branch it adopts is behind its base, and names a `gh` authentication failure instead of a generic error.
- Two loops fetching in one clone at once no longer fail on the remote-tracking ref race.
- `machine setup` no longer advises running `mise activate`.
- A failed connection now says why, once: whether the box answered but refused the key, or did not answer, and what to check. `file:` references expand a leading `~/`.
- On-box command hints name the box they were relayed to, so a suggested command can be pasted on your machine as is.
- Bare clones track `origin`'s branches, and sessions are cut from `origin/<base>` rather than a stale local copy.
- Placement sources are staged byte for byte, so a key keeps its final newline.
- The mise fragment quotes keys that are not bare and escapes control characters.
- The requested tailnet node name is always a valid DNS label.
- Setup writes its marker atomically and records each phase before reporting it, so an interrupted run resumes from the right place.
- `machine status`, a re-run of `machine setup` and `machine upgrade` no longer fail on a box first set up as `root`. Each command now ships its scripts to a temp directory of its own instead of a fixed root-owned path.
- `--access tailscale` over a `root` bootstrap login no longer fails after hardening closes root login. Every stage after the bootstrap reaches the box as the `smith` user.
- `smith loop run <box>` reads the issue with `gh` under `mise exec`, so its preflight works from your machine on a box whose `gh` comes from the blueprint. → [What a shell on the box gets](../on-box.md#what-a-shell-on-the-box-gets)
- The `git fetch` before a session or loop cuts a new branch runs under `mise exec` in the repo's directory, so a private repo whose credential helper is a declared `gh` fetches from a relayed smith. → [Cutting, fetching and `--base`](../sessions.md#cutting-fetching-and---base)
- Setup's closing re-run line always names `--blueprint`, the staged one when there was one, since a box built from a blueprint refuses a re-run without it. → [Naming a box on setup](../inventory.md#naming-a-box-on-setup)
